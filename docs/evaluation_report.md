> **Data disclaimer.** All results in this report were produced on a

## 1. Objective

This report evaluates the WP5 classical anomaly detector in two complementary
ways:

1. **Standard detection evaluation** — detection rate, false alarm rate,
   precision, and F1 on a labelled normal/anomalous evaluation split.
2. **Adversarial (red-team) evaluation** — treating the detector as a security
   control and actively trying to make genuinely anomalous inputs evade it, to
   characterise its blind spots.

The second part reflects a penetration-testing / red-teaming mindset: a defence
is only as good as what it misses against an adversary who understands it.

---

## 2. Detector under test

`StatisticalAnomalyDetector` (see `src/detectors/classical/statistical_detector.py`).

- Follows the shared `AnomalyDetector` interface (`fit` / `predict` /
  `score_samples`), convention `0 = normal`, `1 = anomalous`, higher score =
  more anomalous.
- Pluggable scoring strategies: `robust_zscore` (median + MAD, `max`
  aggregation — default), `zscore`, and `mahalanobis` (multivariate, uses the
  inverse covariance matrix).
- Threshold established from training scores (here: 99th percentile).

| Item | Value |

Reproduce with:

```bash
python -m src.detectors.classical.demo
```

## 4. Standard detection results

| Scoring strategy | Threshold | Detection rate | False alarm rate | Precision | F1 |
|---|---|---|---|---|---|
| `robust_zscore` | 3.211 | 1.000 | 0.015 | 0.943 | 0.971 |
| `zscore` | 3.116 | 1.000 | 0.018 | 0.935 | 0.966 |
| `mahalanobis` | 4.006 | 1.000 | 0.022 | 0.917 | 0.957 |

**Reading.** On the "obvious" anomalies (large deviations and spikes), all three
strategies detect every anomaly (detection rate = 1.0) with a low false alarm
rate (1.5–2.2%). On this benign evaluation set, `robust_zscore` has the best
precision/F1. Taken alone, this would suggest the simple per-feature baseline is
the best choice — the adversarial evaluation below shows why that conclusion is
incomplete.

## 5. Adversarial (red-team) evaluation

Each attack crafts inputs that are genuinely anomalous (ground truth = 1) but
designed to **evade** detection. The metric is the **evasion rate**: the
fraction of crafted anomalies the detector labels as normal. Higher = worse for
the defender. All attacks operate on the numeric feature representation only;
no real platform is touched.

### 5.1 Attacks

| Attack | Idea |
|---|---|
| `slow_drift` | Gradually push one feature away from nominal; measure how far the drift grows before detection. |
| `boundary_probe` | Randomised perturbations scaled around the decision boundary. |
| `single_feature_evasion` | One large single-feature anomaly, optionally with masking noise on the rest. |
| `distributed_deviation` | Split one large deviation budget across all features so each stays small individually. |

### 5.2 Results — `robust_zscore` (default, `max` aggregation)

| Attack | Evasion rate | Evaded / total | Note |
|---|---|---|---|
| `slow_drift` | 0.500 | 25 / 50 | Drift undetected until offset ≈ 3.06 |
| `boundary_probe` | 0.425 | 85 / 200 | Borderline anomalies slip through often |
| `single_feature_evasion` (no mask) | 0.000 | 0 / 100 | Caught reliably |
| `single_feature_evasion` (mask=3.0) | 0.000 | 0 / 100 | Masking does not help the attacker |
| **`distributed_deviation`** | **1.000** | **100 / 100** | **Complete evasion** |

### 5.3 Results — `mahalanobis` (multivariate)

| Attack | Evasion rate | Evaded / total | Note |
|---|---|---|---|
| `slow_drift` | 0.640 | 32 / 50 | Slightly worse on single-axis drift |
| `boundary_probe` | 0.290 | 58 / 200 | Better than `robust_zscore` |
| `single_feature_evasion` (no mask) | 0.000 | 0 / 100 | Caught reliably |
| `single_feature_evasion` (mask=3.0) | 0.000 | 0 / 100 | Caught reliably |
| **`distributed_deviation`** | **0.000** | **0 / 100** | **Fully resisted** |

## 6. Key finding

The standard metrics (§4) favour `robust_zscore`. The adversarial evaluation
reverses that conclusion against an adaptive adversary:

| Attack | `robust_zscore` | `mahalanobis` |
|---|---|---|
| single-feature (large) | 0.00 evasion | 0.00 evasion |
| **distributed deviation** | **1.00 evasion** | **0.00 evasion** |

**Why it happens.** `robust_zscore` aggregates per-feature deviations with
`max`, so it only reacts to the single worst feature. An attacker who knows this
can spread the same total deviation across all six features — each feature stays
below the threshold while the overall observation is clearly abnormal. Every one
of the 100 crafted anomalies passed as normal. `mahalanobis` evaluates the joint
distribution via the covariance matrix, so a coordinated multi-feature
deviation still lands far from the normal region and is caught.

**Implication.** When the threat model includes an adversary who understands the
detector (a realistic assumption for a security control), a multivariate scoring
strategy is preferable despite its marginally lower score on benign data.
Evaluating only on non-adaptive anomalies would have hidden a total-evasion
vulnerability.

---

## 7. Documented limitations of the classical baseline

- **`max` aggregation is evadable** by distributing a deviation across features
  (demonstrated: 100% evasion). Mitigation: use `mahalanobis`, or add a
  secondary aggregate (e.g. sum/mean) alongside `max`.
- **Slow drift** (50–64% evasion) is hard for a static-threshold detector; it
  reacts only once the cumulative offset is large. Temporal modelling (out of
  current scope) would be needed.
- **Borderline anomalies** near the threshold evade at 29–43%; this is inherent
  to any single hard threshold and is a precision/recall trade-off.
- **No temporal/sequence modelling** — each observation is scored
  independently (threat-model scenarios §5.3, §5.4 not covered).
- **Synthetic data only** — these conclusions must be re-validated on real WP4
  data.

---

## 8. Recommendations

1. **Default to `mahalanobis`** (or a hybrid aggregation) when an adaptive
   adversary is in scope.
2. **Report adversarial metrics alongside standard metrics** in the WP7
   comparison with the AI/ML detector — benign metrics alone can mislead.
3. **Feed these attacks back to WP3** as concrete, testable threat scenarios
   (distributed deviation, slow drift).
4. **Re-run the full suite on real WP4 data** once available; current numbers
   are a synthetic-data baseline only.
